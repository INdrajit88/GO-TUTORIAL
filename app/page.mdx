In this tutorial, we’ll run an Echo-based URL shortener with PostgreSQL and use Keploy to capture and replay API testcases.

I’ll also cover a small configuration issue that can easily come up when switching between Docker and a local Linux/WSL setup: the PostgreSQL host.

By the end, you’ll have:

* An Echo + PostgreSQL application running locally.
* API requests captured as Keploy testcases.
* PostgreSQL interactions captured as mocks.
* The captured testcases replayed without manually creating database mocks.

---

## Prerequisites

Before getting started, make sure you have:

* **Go** installed.
* **Docker** installed and running.
* **Keploy** installed.

If Keploy is not installed yet, follow the [Keploy installation guide](https://keploy.io/docs/server/installation/).

---

## Get the Sample Application

Clone the sample repository and install its dependencies:

```bash
git clone https://github.com/keploy/samples-go.git
cd samples-go/echo-sql
go mod download
```

The sample is a simple URL shortener built with Echo and backed by PostgreSQL.

---

## Process 1: Docker Compose Workflow

In this first workflow, both the application and PostgreSQL run containerized through Docker Compose, with Keploy recording network interactions between them.

### Update the PostgreSQL Host

Before starting the application, open `main.go` and update the PostgreSQL host from:

```text
localhost
```

to:

```text
postgres
```

This matters because the application is running inside Docker. In that environment, `localhost` points to the application container itself.

`postgres` is the hostname of the PostgreSQL service on the Docker Compose network.

<NetworkArchitecture />

<Callout type="tip" title="Understanding Compose DNS">

The correct PostgreSQL host depends on where your application is running. Inside Docker Compose, services communicate over a private bridge network using container service names. We’ll switch it back to `localhost` in the local Linux/WSL setup later.

</Callout>

<Heading level={3} id="build-the-application-docker">Build the Application</Heading>

Create the application binary:

```bash
go build -o echo-psql-url-shortener
```

---

### Start Recording with Keploy

Start the application through Keploy:

```bash
keploy record -c "docker compose up" --container-name "echoApp" --build-delay 50
```

The `--build-delay` option gives Docker some extra time to build images and start the services before Keploy begins capturing traffic.

You can skip it when your services are already running.

### Generate a Testcase

With the application running, send a request to create a shortened URL:

```bash
curl --request POST \
  --url http://localhost:8082/url \
  --header 'content-type: application/json' \
  --data '{
  "url": "https://github.com"
}'
```

You should get a response similar to:

```json
{
  "ts": 1647802058801841100,
  "url": "http://localhost:8082/GuwHCgoQ"
}
```

The timestamp changes between requests, so Keploy handles such dynamic values during testing.

#### Test the Redirect Endpoint

Use the generated short URL:

```bash
curl http://localhost:8082/GuwHCgoQ
```

You can also open the URL directly in your browser.

At this point, Keploy has captured both API interactions.

<Screenshot
  src="/screenshots/04-curl-requests.webp"
  alt="Terminal showing curl requests and responses for URL shortener"
  caption="Generating real API traffic with curl: creating a shortened URL and testing the redirect."
/>

### Stop Recording

Once you have finished sending the test requests, stop the Keploy capture session:

1. Return to the terminal where `keploy record` is running.
2. Press `Ctrl + C` to stop capturing.

Keploy catches the interrupt signal, flushes the intercepted network packets, and writes the captured testcases and database mocks to disk in the `keploy/` directory.

<Callout type="info" title="Stop Compose containers before replaying">

Before replaying testcases with `keploy test`, bring down the currently running Docker Compose services so that container ports and network interfaces are freed:

```bash
docker compose down
```

</Callout>

---

### Check the Generated Testcases

The captured testcases are written to the Keploy directory.

Along with the HTTP testcases, Keploy also records the PostgreSQL interactions generated while processing those requests.

This means you don't have to manually create mocks for every database operation.

Your generated data will look roughly like:

```text
keploy/
├── tests/
└── mocks/
```

The exact files may vary depending on the recorded requests.

### Replay the Testcases

Once the recording is complete, run the captured testcases:

```bash
keploy test -c "docker compose up" --container-name "echoApp" --build-delay 50 --delay 10
```

Keploy replays the recorded API requests and uses the captured PostgreSQL interactions during the test.

This gives you a repeatable test flow without manually setting up database mocks for each testcase.

## Process 2: Local Linux/WSL Workflow

In this alternative workflow, the Go application runs directly on your local Linux or WSL machine while keeping PostgreSQL inside Docker.

This setup requires adjusting the database host and running Keploy with appropriate permissions against the compiled binary.

### Start PostgreSQL

Start only the PostgreSQL service:

```bash
docker compose up -d postgres
```

Now PostgreSQL is running inside Docker, while the Go application will run directly on your host machine.

<Callout type="tip" title="Run PostgreSQL in the background">

Using the `-d` flag runs the PostgreSQL container detached in the background, keeping your active terminal free for compiling and running the Go application.

</Callout>

### Change the PostgreSQL Host

Because the application is now running outside Docker, change the PostgreSQL host in `main.go` back to:

```text
localhost
```

This is the key difference between the two setups:

| Application | PostgreSQL Host |
| --- | --- |
| Application inside Docker | `postgres` |
| Application running locally | `localhost` |

If the application cannot connect to PostgreSQL, this is one of the first things to check.

<Screenshot
  src="/screenshots/02-postgres-host-fix.webp"
  alt="main.go open in an editor with the PostgreSQL host set to localhost"
  caption="Line 48 in main.go — setting the PostgreSQL host to localhost so the host-running binary can reach the mapped PostgreSQL container port."
/>

<Callout type="tip" title="Why localhost works for Local Linux/WSL">

Because the PostgreSQL container publishes port `5432:5432` directly to the host machine, the Go binary running outside Docker communicates through the standard `localhost:5432` loopback address without requiring container network resolution.

</Callout>

### Build the Application

Create the application binary:

```bash
go build -o echo-psql-url-shortener
```

### Start Keploy Recording

Run Keploy against the binary:

```bash
sudo -E PATH=$PATH keploy record -c "./echo-psql-url-shortener"
```
These requests will be captured by Keploy along with the PostgreSQL interactions generated by the application.

<Screenshot
  src="/screenshots/06-recorded-tests.webp"
  alt="Keploy capturing local binary requests into test-set-1"
  caption="Keploy capturing API calls and PostgreSQL wire-level exchanges from the local binary into test-set-1."
/>

<Callout type="tip" title="Why sudo -E PATH=$PATH is required on Linux/WSL">

On Linux and WSL2, Keploy leverages eBPF (Extended Berkeley Packet Filter) to attach hooks to kernel network sockets and capture PostgreSQL wire traffic transparently. Loading eBPF programs requires root privileges (`sudo`), while `-E PATH=$PATH` ensures the user's Go binary and toolchain paths are preserved.

</Callout>

## Keploy Test Replay Execution Workflow

How Keploy executes tests: replaying recorded requests, serving mocked database responses, and validating application behavior without live dependencies.

<Screenshot
  src="/screenshots/08-keploy-flow.webp"
  alt="Keploy test replay execution workflow diagram"
  caption="How Keploy executes tests: replaying recorded requests, serving mocked database responses, and validating application behavior without live dependencies."
/>

When you run `keploy test`, Keploy doesn't just execute an arbitrary test script—it orchestrates an isolated, wire-level replay environment that simulates client traffic while transparently mocking backend dependencies.

### Step-by-Step Replay Architecture

The flowchart above illustrates each stage of Keploy's replay lifecycle:

1. **Recorded Test Ingestion (`keploy/` directory)**  
   Keploy loads the captured YAML test suites and mock files generated during `keploy record`. The test files (`tests/`) store the inbound HTTP request contracts (HTTP method, URI, headers, body) alongside expected responses. The mock files (`mocks/`) store the exact binary/wire-level exchanges between the application and external services (PostgreSQL queries, bind parameters, and result sets).

2. **Application Startup in Test Mode**  
   Keploy launches the target application—either via `docker compose up` or directly by running the compiled local binary. The application runs its normal production code:
   - No mock frameworks or interfaces need to be injected into Go code.
   - No conditional test flags or dummy endpoints are required.
   - The application functions as if connecting to live infrastructure.

3. **Ingress: Replaying Recorded API Requests**  
   Keploy acts as an intelligent HTTP client, sequentially or concurrently firing recorded requests (such as `POST /url` to shorten a URL and `GET /:id` to follow the redirect) into the application port (`8082`).

4. **Egress: Transparent Database Mocking**  
   When the Go application executes queries against PostgreSQL (e.g. `INSERT INTO urls...` or `SELECT url FROM urls WHERE id = ...`), Keploy intercepts the outgoing TCP connection at the network/kernel layer. Instead of forwarding the query to a real PostgreSQL instance:
   - Keploy matches the outgoing SQL query against its pre-recorded `mocks.yaml`.
   - It instantly returns the recorded database response over the wire.
   - **The test runs completely offline—no PostgreSQL container or live database instance needs to be running or pre-seeded.**

5. **Actual Application Response Capture**  
   The application processes the mocked database data through its standard business logic and generates an HTTP response. Keploy captures this response directly from the network socket.

6. **Response Comparison & Dynamic Noise Filtering**  
   Keploy evaluates the actual response against the recorded baseline:
   - It verifies the HTTP status code (e.g., `200 OK` or `307 Temporary Redirect`).
   - It validates headers and response JSON schemas.
   - **Smart Noise Filtering:** Keploy automatically identifies dynamic fields (like the timestamp `"ts": 1645540022`, random tokens, or UUIDs) and ignores them during assertion so non-deterministic values don't trigger false positives.

7. **Verification & Test Verdict (`PASS ✅`)**  
   - **Success:** If the application behavior matches the recorded contract, the test passes with zero flaky failures.
   - **Regression Detection:** If a recent code change altered the payload structure, dropped an expected field, or broke database query sequences, Keploy displays a clean terminal diff pinpointing the exact regression.

### Replay Architecture Comparison

| Feature | Traditional Integration Testing | Keploy Zero-Code Replay |
| --- | --- | --- |
| **External Dependencies** | Requires live PostgreSQL, Docker containers, seed scripts | 100% mocked at network layer; no live DB required |
| **Mock Maintenance** | Developers write & maintain hundreds of mock interfaces | Recorded automatically from real network traffic |
| **Test Flakiness** | High (caused by database state, leftover data, race conditions) | Zero (completely deterministic and idempotent) |
| **Execution Speed** | Slow (waits for database network I/O and disk writes) | Fast (instant wire-level mock responses in memory) |
| **CI/CD Complexity** | Heavy container orchestration & database provisioning | Lightweight single-binary test runner (`keploy test`) |

<Callout type="tip" title="Hermetic testing in CI/CD pipelines">

Because Keploy mocks all PostgreSQL queries at the network level, you can run your complete regression test suite inside lightweight CI/CD runners (like GitHub Actions) without setting up database service containers, managing migrations, or handling secret credentials.

</Callout>
