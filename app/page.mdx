### Why this sample and not a hello-world

Because it has the two things that make Keploy interesting rather than merely impressive:
an HTTP surface, and a real dependency hiding behind it.

<TerminalBlock language="text" title="the sample">{artifacts.stack}</TerminalBlock>

One route shortens a URL, the other redirects, and both touch PostgreSQL. If this were
HTTP-only you'd shrug and move on. It's the database calls that you'd otherwise have to
fake — and those get captured too.

</Step>

<Step number={2} title="Point the app at Postgres">

This is the step I got wrong, so let's settle it before anything starts.

Open `main.go` and find the host the app dials for PostgreSQL. In the Compose workflow it
has to be the service name — `postgres` — and not `localhost`.

<Screenshot
  {...screenshots.postgresFix}
  alt="main.go open in an editor with the PostgreSQL host set to the Compose service name"
  caption="Line 48 in main.go — the one-word change that decides whether the app can find its database."
/>

Here's the why. On a Compose network every service is reachable by its service name, so the
Go container resolves `postgres` straight to the database container. `localhost` inside that
same container means *the container itself*, where nothing is listening on 5432. The word
looks correct, reads correct, and is correct on your laptop — which is exactly why it's
annoying.

<Callout type="tip" title="Once you know the rule it stops being magic">

Service discovery by name is a Compose network feature, not something the Go app
implements. After a while `postgres`, `redis` and `db` in connection strings stop looking
like incantations and start being the obvious way to address a sibling container.

</Callout>

</Step>

<Step number={3} title="Start Keploy in record mode">

Now start the stack *through* Keploy, rather than starting Compose yourself:

<CommandBlock title="record mode">{commands.record}</CommandBlock>

One command doing three separate jobs, and it's worth knowing which is which:

- `-c "docker compose up"` is what Keploy runs for you, so the stack comes up exactly as it
  would have otherwise.
- `--container-name "echoApp"` says which container in that stack holds the app to observe.
  Compose starts more than one; only one of them is the API.
- `--build-delay 50` buys the stack time to build images and get PostgreSQL accepting
  connections before Keploy starts watching. On a cold Docker cache, none of that is
  instant.

**What you should see:** the Compose stack come up and Keploy settle into recording. Nothing
is being tested yet. Keploy has put itself in the application's execution flow, so it can
watch requests arrive and database calls go back out:

<TerminalBlock language="text" title="the compose stack">{artifacts.compose}</TerminalBlock>

<Callout type="info" title="Record mode is a recorder, not a test runner">

This tripped me up for a minute. Keploy isn't reading my Go code and generating tests from
it, and it isn't guessing at my API. It's waiting for me to *use* the application and
writing down what happens. Verification is a different command, and it comes later.

</Callout>

</Step>

### What Keploy actually captured

This is the part worth slowing down for.

I sent `POST /url`. The Echo handler processed it and talked to PostgreSQL to store the
mapping. Keploy watched the whole thing — request, response, and the database calls in
between — and wrote down enough to reproduce it.

Now compare that with what I'd normally do to test the same endpoint:

- construct the request
- set the headers
- build the body
- assert the expected response
- and mock the database, because the test can't hit a real one

I did none of that. I made one API call and Keploy took notes.

<Callout type="success" title="The moment it clicked">

The test gets created by using the application normally. There's no separate step where I
transcribe what I did into a test file — the real interaction *is* the source material.

</Callout>

</Step>

<Step number={5} title="Test the shortened URL">

Now do what an actual user does next: follow the link. Swap in the ID your own `POST`
returned.

<CommandBlock title="follow the short url">{commands.getShortUrl}</CommandBlock>

**What you should see:** a redirect to the original URL. The same thing works from a browser
at <code>{endpoints.follow}</code>, which is a useful reminder — Keploy isn't recording
`curl`. It's recording what the application saw.

### Why that's a second test case and not a duplicate

Because it's a second behavior. The first request wrote a row; this one reads it back and
issues a redirect. Different route, different handler, different database call, different
response shape. Keploy treats each recorded interaction as its own scenario, so the test
set now describes two genuinely different things the API does:

<TerminalBlock language="text" title="recorded scenarios">{artifacts.scenarios}</TerminalBlock>

That's what makes this scale past a demo. The more of the application you actually use
while recording, the more of it is covered when you replay. Coverage here is a function of
how thoroughly you poke the API, not of how much test code you write.

</Step>

### Test cases versus mocks

Two different things, and keeping them straight is most of the mental model:

- **`tests/`** holds the recorded test cases. Each file is one interaction: what came in,
  what went back out.
- **`mocks.yaml`** holds the recorded dependency behavior — the PostgreSQL calls Keploy saw
  the app make.

<Callout type="info" title="Why the mocks matter more than they look">

The test case says what the interaction looked like. The mocks supply the dependency
behavior needed to reproduce it. That's why there's no fake PostgreSQL to write: the real
one was observed, and its answers were kept.

</Callout>

Both files are YAML. You can open them, read them, and diff them in a PR — nothing here is
an opaque binary blob, which matters the first time a test fails and you need to know why.

</Step>

<Step number={7} title="Replay the recorded tests">

Now the recording earns its keep:

<CommandBlock title="replay">{commands.test}</CommandBlock>

Same stack, same container, same warm-up as the record command. The new flag is
`--delay 10` — how long Keploy waits for the app to be ready before it starts firing
recorded requests at it.

### What happens during replay

Keploy brings Compose up again and works through the test cases one at a time. For each one
it replays the recorded request against your application, serves the recorded dependency
responses back to it, and then compares what the app actually did with what it did during
recording.

<TerminalBlock language="text" title="replay">{artifacts.replay}</TerminalBlock>

Two things I no longer have to do:

- re-send the API requests by hand
- recreate the PostgreSQL interactions the app expects to have

<Callout type="info" title="Record once, replay forever">

The recording is a reproducible description of an interaction. `keploy test` uses it to
check whether the app still behaves the same way — which is precisely what a regression
test is for, and precisely why these files belong in version control next to the code.

</Callout>

</Step>

<Step number={8} title="Understand the workflow">

Step back from the individual commands and it's one loop:

<Screenshot

Reduced to four moves:

1. Start the application.
2. Use the API the way a real caller would.
3. Keploy records what happened.
4. Keploy replays it as a test.

The shift worth noticing is the starting point. Most testing workflows begin with test code
you write before or alongside the behavior it describes. This one begins with **observed
behavior**, and the test is derived from it. Different direction of travel, and it changes
what testing costs you.

<Step number={9} title="Why this is useful for Go developers">

An API test in Go is rarely just the HTTP request. To make it mean anything you usually end
up defining:

- the request itself
- headers
- body
- the expected response
- the database state it assumes
- the behavior of anything else it calls
- mocks for all of the above

That's a lot of scaffolding around a behavior that already exists and already works — and
it's scaffolding you get to maintain again every time the response shape changes. I have
never once enjoyed the mocking half.

<Screenshot
  {...screenshots.comparison}
  alt="Comparison of the Keploy record-and-replay workflow against writing API tests and mocks by hand"
  caption="Two workflows, and the difference is which one you have to maintain."
/>

Keploy captures the interaction while you use the application and keeps what's needed to
replay it. So the work becomes: use the app → capture the interaction → reuse it as a test,
instead of: write everything by hand → build mocks by hand → maintain all of it by hand.

Being honest about the limits, because this isn't magic: it won't design your edge cases,
and it won't tell you what *should* happen — only what did happen. If your handler has a
bug, Keploy will faithfully record the bug and then faithfully defend it. What it's
genuinely good at is turning realistic API interactions into reproducible regression tests,
cheaply, for exactly the endpoints that are tedious to test by hand.

</Step>

<Callout type="warning" title="Don't edit recorded expectations just to make a test pass">

A failing replay is information, and it's tempting to delete the information. Something
about the app's behavior changed since the recording — sometimes that's a bug you wanted
caught, sometimes it's an intentional change that means the test case should be
re-recorded. Work out which one it is *before* touching the test data. Otherwise the suite
stays green and quietly stops meaning anything, which is worse than not having it.

</Callout>
